# PDF capability matrix

This is the Phase 0 capability matrix called for in the repository
docs/PLAN.md's phased plan: a single place recording, for each area of PDF
functionality, what this project targets supporting and what phase is
expected to deliver it. It exists so that "does pdf-viewer support X?"
has one authoritative, checkable answer instead of requiring an
archaeology of commit history or source comments, and so that a decision
to leave something permanently unsupported is recorded as a decision
rather than discovered by accident.

**Status legend**

| Status | Meaning |
| --- | --- |
| Not started | No design decision or code yet. |
| Planned | Targeted for a specific phase below, no code yet. |
| Partial | Some code exists; coverage is incomplete. See notes. |
| Done | Implemented and covered by tests. |
| Non-goal | Deliberately out of scope; see the docs/PLAN.md's "Non-goals for the Initial Release" section. |

This table should be updated in the same change that changes a
capability's support level — treat a code change that isn't reflected
here as incomplete. See [docs/PLAN.md](../docs/PLAN.md) for the phased plan
and its Progress Log for what was actually built in each phase.

## PDF versions

| Capability | Target phase | Status | Notes |
| --- | --- | --- | --- |
| PDF 1.4–1.7 core structure (classic xref tables, classic trailers, incremental updates via /Prev, recovery scan for a corrupted xref table) | Phase 1 | Partial | Implemented in `internal/parser`; see its package doc comment. "Partial" because broader real-world compatibility is still growing, not because the mechanism itself is incomplete. |
| PDF 1.5+ cross-reference streams and object streams | Phase 2 (moved from Phase 1) | Done | Implemented in `internal/parser` (`xrefstream.go`, `objstream.go`), now that Flate decoding exists (`internal/filter`). A document may freely mix classic and stream-based cross-reference sections across its `/Prev` chain. Hybrid-reference files (a classic table plus a supplementary `/XRefStm` for stream-unaware readers) are not specially handled - objects only reachable via `/XRefStm` are not found - but this is rare in practice and does not cause an error, only a missing object (resolved as null). |
| PDF 2.0 (ISO 32000-2) structural changes | Phase 6 | Not started | Phase 6 decision (see the docs/PLAN.md's "Supported PDF versions" section): this project's supported range for its initial release is PDF 1.4-1.7. PDF 2.0 is largely a clarified superset of 1.7 for the structural/content features this project implements, so most 1.7-targeting code is expected to already handle a 2.0 file's shared structure correctly - but this has not been verified against a real 2.0 corpus, and PDF 2.0-specific additions (e.g. new encryption revisions, `/AF` associated files) are unimplemented. Revisit once a 2.0 test corpus exists. |
| Linearized ("fast web view") files | Not scheduled | Not started | Linearization is an optimization hint or convention layered on top of standard structure, not the file's ground truth; a linearized file must still be readable using vanilla xref/trailer parsing, so this project treats it as automatically handled rather than as a scheduled feature. |

## Encryption

| Capability | Target phase | Status | Notes |
| --- | --- | --- | --- |
| Unencrypted documents | Phase 1 | Done | Baseline; every fixture and real-world file this project has been tested against is unencrypted. |
| Detecting and rejecting an encrypted document this package cannot open | Phase 6 | Done | Implemented in `internal/parser` (`Open`/`setupEncryption`): a document that needs a password this package cannot supply, or that names a security handler other than Standard, is rejected immediately with an error wrapping the `ErrEncrypted` sentinel (itself wrapping `ErrUnsupported`) - see the root package's errors.go. This is a clear, immediate failure in place of the confusing garbled-data errors that would otherwise surface later, the first time some still-encrypted stream or string was read. |
| Standard security handler, empty user password ("owner-password-only" protected files) | Phase 7a | Done | Implemented in `internal/crypt` (key derivation, RC4 and AES-128/256 decryption for revisions 2-6, no CGO or third-party dependency - see that package's doc comment) and wired into `internal/parser` (`Open`/`setupEncryption`, `Document.Resolve`). Common in practice (permissions-only protection); such a document now opens and renders exactly as its unencrypted equivalent would - permissions themselves are not enforced, since this package only decrypts, per its scope as a renderer. See docs/PLAN2.md's Phase 7. |
| Standard security handler, non-empty user password | Phase 7b | Done | `Open`/`OpenFile` now accept the new `WithPassword(string)` `OpenOption` (root package's options.go), threaded through `internal/parser.Open`/`internal/parser.WithPassword` to `internal/crypt.New`, which tries it as the document's user password (revisions 2-6, same key-derivation machinery as Phase 7a, now given a real password instead of always empty). A correct password opens the document exactly as Phase 7a's empty-password case does; a wrong or missing password fails with an error wrapping `ErrEncrypted`, distinguishable by message text ("none was supplied" vs. "the supplied password is incorrect") though not by a second sentinel - this project's error taxonomy deliberately keeps exactly four top-level sentinels (see the root package's errors.go). Recovering a user password from a supplied *owner* password (ISO 32000-1 Algorithm 7) is out of this phase's scope - see internal/crypt's `New` doc comment. |
| Public-key security handler | Not scheduled | Not started | No known demand driving this; revisit only if a real use case appears. |

## Filters (stream and string decoding)

| Capability | Target phase | Status | Notes |
| --- | --- | --- | --- |
| ASCII85Decode, ASCIIHexDecode | Phase 2 | Done | Implemented in `internal/filter` (`ascii85.go`, `asciihex.go`). |
| FlateDecode (with predictors) | Phase 2 | Done | Implemented in `internal/filter` (`flate.go`, `predictor.go`). Both PNG (predictor 10-15) and TIFF (predictor 2) predictors are supported for `/BitsPerComponent` 1, 2, 4, 8, and 16. |
| RunLengthDecode | Phase 2 | Done | Implemented in `internal/filter` (`runlength.go`). |
| LZWDecode | Phase 2 | Partial | Implemented in `internal/filter` (`lzw.go`) via the standard library's `compress/lzw`, whose `MSB` order is explicitly documented as PDF-compatible. "Partial" because only the default `/EarlyChange 1` is supported - `/EarlyChange 0` returns an error wrapping `ErrUnsupported`, since the standard library offers no way to select that variant. PNG/TIFF predictors are supported here too, sharing `predictor.go` with FlateDecode. |
| DCTDecode (JPEG) | Phase 3 | Done | Implemented in `internal/filter` (`dct.go`) via the standard library's `image/jpeg`: baseline and progressive JPEG, grayscale/YCbCr/CMYK (Adobe) component layouts all supported since Go's decoder already handles each. Bounded via `jpeg.DecodeConfig` (reads only the header) before committing to a full decode, so a maliciously huge declared image size is rejected before an oversized allocation. |
| CCITTFaxDecode | Phase 3 (added later) | Done | Common in scanned/fax-derived PDFs; no standard-library decoder exists, so `internal/filter` (`ccitt.go`) implements one from scratch, closely porting the well-proven xpdf/pdf.js CCITT decoder's Huffman tables and row-decoding algorithm (see that file's own doc comment for provenance and license). Group 4 (`/K` < 0, pure 2D/T.6 - the common case for scan-to-PDF output), Group 3 1D (`/K` 0), and Group 3 mixed 1D/2D (`/K` > 0) are all supported, along with `/BlackIs1`, `/EncodedByteAlign`, `/EndOfLine`, and `/EndOfBlock`. |
| JBIG2Decode | Phases 8 and 9 | Partial | Common in scan-to-PDF and OCR output, where it beats CCITT Group 4 on text-heavy pages; no standard-library decoder exists, so `internal/filter` implements one from scratch (`jbig2.go`, `jbig2segment.go`, `jbig2generic.go`, `jbig2arith.go`, `jbig2symbol.go`, `jbig2text.go`, `jbig2refine.go`, `jbig2mq.go` - see those files' doc comments for provenance). Supported: PDF's embedded segment organization, segment header parsing and referred-to segment resolution, arithmetic-coded generic regions (all four GBTEMPLATEs, arbitrary adaptive-template pixel positions, TPGDON typical prediction, multi-region compositing), the arithmetic integer decoding procedures (T.88 Annex A), symbol dictionaries and text regions (all four reference corners, transposed regions, multi-row strips, dictionary chaining), generic refinement regions (both GRTEMPLATEs, TPGRON) including a text region's per-instance SBREFINE and a symbol dictionary's SDREFAGG refinement and aggregate forms, and `/JBIG2Globals` (resolved through `internal/parser.Document.DecodeStream`, which supplies `internal/filter`'s `StreamResolver`). "Partial" because Huffman-coded symbol dictionaries and text regions, halftone regions and pattern dictionaries, MMR-coded generic regions, symbol dictionaries importing another segment's arithmetic contexts, and unknown-length segments each return an error wrapping `ErrUnsupported` naming the specific feature rather than mis-decoding. |
| JPXDecode (JPEG 2000) | Phase 14 | Not started | Not scheduled before Phase 14: a full wavelet-based JPEG 2000 decoder is a substantially larger undertaking than JBIG2, and in practice JPX appears in narrower verticals (geospatial, medical imaging, archival PDF/A) rather than general office documents. |
| Crypt filter | Not scheduled | Not started | Depends on encryption support above. |

## Content streams and graphics

| Capability | Target phase | Status | Notes |
| --- | --- | --- | --- |
| Content stream operator parsing | Phase 2 | Done | Implemented in `internal/content` (`operator.go`); reuses `internal/syntax` for operand syntax. Inline images (`BI`/`ID`/`EI`) are explicitly detected and rejected as unsupported (Phase 3) rather than silently misparsed. |
| Graphics state stack (`q`/`Q`), coordinate transforms (`cm`) | Phase 2 | Done | Implemented in `internal/graphics` (`state.go`, `matrix.go`). |
| Path construction (`m`/`l`/`c`/`v`/`y`/`h`/`re`) | Phase 2 | Done | Implemented in `internal/graphics` (`path.go`). Bézier curves are flattened into a fixed number of line segments for deterministic rasterization. |
| Path painting: fill, nonzero and even-odd (`f`/`F`/`f*`/`B`/`B*`/`b`/`b*`) | Phase 2 | Done | Implemented in `internal/raster`'s scanline coverage rasterizer (`scanline.go`). |
| Path painting: stroke (`S`/`s`), line width/cap/join | Phase 2 | Partial | Implemented via `internal/graphics.StrokeToFill` (`stroke.go`): a stroke is converted to its filled outline before rasterization. Line width and caps (butt/round/square) are exact; joins are always rendered as round joins regardless of the requested join style - true miter (with miter-limit fallback to bevel) and bevel join geometry are not yet implemented. Dash patterns (`d`) are parsed and ignored; every stroke is solid. |
| Clipping (`W`/`W*`) | Phase 2 | Partial | Implemented in `internal/graphics` (`state.go`'s `Clips`) and `internal/raster` (coverage-multiplication intersection). Multiple simultaneously active clips are supported, but combined via multiplying each clip's independently anti-aliased coverage rather than true polygon-boolean intersection - an approximation, exact for non-anti-aliased (opaque-interior) clip regions. |
| Solid color: DeviceGray/RGB/CMYK (`g`/`G`/`rg`/`RG`/`k`/`K`) | Phase 2 | Done | Implemented in `internal/content` (`interpret.go`). CMYK uses the PDF specification's own baseline (non-color-managed) conversion formula. |
| `sc`/`SC`/`scn`/`SCN` with a resolved `/ColorSpace` resource | Phase 2/3/5 | Partial | `internal/content` (`colorspace.go`) now resolves `cs`/`CS`'s named color space via `internal/image.ResolveColorSpace` - the same logic an image's own `/ColorSpace` uses - so `sc`/`scn`/`SC`/`SCN` convert correctly through a resolved Separation/DeviceN/Lab/Indexed/ICCBased/CalGray/CalRGB space, not just the three Device families. When no color space was selected, the selected one could not be resolved, or its component count does not match the operands given, this falls back to inferring DeviceGray/RGB/CMYK directly from operand count (1, 3, or 4), exactly as before. "Partial" because Pattern is still not usable as a fill/stroke paint source (a pattern name operand, `scn`/`SCN` with `/Pattern`, is still explicitly detected and rejected as unsupported - remaining Phase 5 work). |
| Image XObjects (`Do` with an `/Image` XObject) | Phase 3 | Done | Implemented in `internal/content` (`image.go`'s `doXObject`), decoding through `internal/image.Decode` and painting via `internal/raster`'s `Canvas.DrawImage` - see the "Images" section below for color-space/mask/decode-array coverage. |
| Inline images (`BI`/`ID`/`EI` operators) | Phase 3 | Done | Implemented in `internal/content` (`operator.go`'s `Parse` calls `inlineimage.go`'s `parseInlineImage`; `image.go`'s `doInlineImage` decodes and paints, sharing all of `internal/image`'s color-space/mask logic with a referenced XObject image). An inline image's raw data length is read via a non-standard `/L` key when present, computed exactly from `/W`/`/H`/`/BPC`/`/CS` for an unfiltered image, or found by scanning for a whitespace-delimited `EI` otherwise - see `parseInlineImage`'s doc comment for the tradeoffs of each. |
| Form XObjects (`Do` with a `/Form` XObject) | Phase 5 | Done | Implemented in `internal/content` (`form.go`'s `doForm`): the form's `/Matrix` (default identity) is concatenated onto the CTM active where `Do` is invoked; its `/BBox` becomes an additional clip; its `/Resources`, when present, replaces the caller's for the form's own content (falling back to the caller's `/Resources` when absent, per the specification). A form's content is recursively interpreted and its resulting `DrawOp`s are flattened directly into the caller's own display list (no intermediate offscreen buffer - see the package's own form.go doc comment for why this is sufficient, unlike a tiling pattern), bounded by `maxFormDepth` (8 levels) against a self-referential or cyclic form. A form's own `/Group` entry (marking it as a transparency group, with isolated/knockout semantics) is not inspected - see "Transparency groups and blend modes" below. |
| Text showing/positioning operators (`BT`/`ET`, `Tc`/`Tw`/`Tz`/`TL`/`Tf`/`Tr`/`Ts`, `Td`/`TD`/`Tm`/`T*`, `Tj`/`TJ`/`'`/`"`) | Phase 4 | Done | Implemented in `internal/content` (`text.go`). Each glyph becomes an ordinary Fill `DrawOp` (`showGlyph`), sharing `internal/raster`'s one rasterization path with vector fills. Text render modes are simplified to two cases: modes 3 and 7 (invisible / clip-only) paint nothing, every other mode (0-2, 4-6) is treated as an ordinary fill - stroked glyph outlines and accumulating a text clip path are not implemented. Only horizontal writing is implemented; a vertical-mode Type0 font (`Identity-V`) still shows text and advances correctly using the horizontal formula rather than vertically. |
| Shading (`sh` operator) | Phase 5, 13a | Partial | Implemented in `internal/content` (`shading.go`'s `doShading`) for axial (`/ShadingType 2`), radial (`/ShadingType 3`), and function-based (`/ShadingType 1`) shadings - see `internal/graphics`'s `Shading` type (`shading.go`) for the geometry/math (axial/radial's line/circle parameter, function-based's direct 2-input `/Function` evaluation over `/Domain`/`/Matrix`) and the "Transparency and advanced graphics" table below for the pattern-fill counterpart. Mesh shadings (Types 4-7 - free-form/lattice-form Gouraud triangle meshes and Coons/tensor patch meshes) are not yet implemented and return an error wrapping `ErrUnsupported` naming the type; see docs/PLAN2.md's Phase 13. Neither a shading's optional `/Background` nor `/BBox` entry is honored for any shading type (a pre-existing simplification, not new to Phase 13). |
| Marked content (`BMC`/`BDC`/`EMC`/`MP`/`DP`) | Not scheduled | Not started | Silently skipped. No rendering-relevant effect for this project's scope (marked content is a metadata/structure mechanism, not a paint operation). |

## Color spaces

| Capability | Target phase | Status | Notes |
| --- | --- | --- | --- |
| DeviceGray, DeviceRGB, DeviceCMYK | Phase 2–3 | Done | Solid-color operators (`g`/`rg`/`k`, `sc`/`scn` by component count) were Phase 2 - see "Content streams and graphics" above. Use as an image color space (decoding pixel samples, including the inline-image abbreviations `/G`/`/RGB`/`/CMYK`) is implemented in `internal/image` (`colorspace.go`). |
| Indexed | Phase 3 | Done | Implemented in `internal/image` (`colorspace.go`'s `resolveIndexed`) over any supported base color space; the lookup table may be a string or a stream (filter-decoded via the same `Resolver.DecodeStream` path as any other stream). An `/Indexed` color space whose base is itself `/Indexed` is rejected as unsupported (not meaningful, and not something real producers emit). |
| ICCBased | Phase 3 | Partial | Implemented in `internal/image` (`colorspace.go`'s `resolveICCBased`) by component count only (`/N` = 1, 3, or 4, aliased to DeviceGray/RGB/CMYK respectively) - this is the documented target behavior ("use the ICC profile's declared alternate/component count... without implementing a full color management engine"), so "Partial" reflects that no actual ICC profile is ever parsed or applied, by design. |
| CalGray, CalRGB | Phase 3 | Partial | Implemented in `internal/image` (`colorspace.go`) as aliases for DeviceGray/DeviceRGB - white point, gamma, and (for CalRGB) matrix are not applied, matching this project's existing non-color-managed CMYK conversion precedent. |
| Lab | Phase 5 | Done | Implemented in `internal/image` (`colorspace.go`'s `resolveLab`/`labToRGB`): standard CIELAB -> CIEXYZ -> linear sRGB -> gamma-encoded sRGB, using the color space's own `/WhitePoint` for the CIEXYZ step but the D65-calibrated standard XYZ->sRGB matrix regardless (a documented approximation - a `/WhitePoint` other than D65, e.g. the D50 common in prepress PDFs, introduces a color cast this project does not chromatically adapt away; full ICC-grade color management is out of scope, matching the existing ICCBased/CalRGB/CalGray precedent). `/Range` (default `[-100 100 -100 100]`) and the fixed `L*` domain `[0 100]` are both honored, including as the color space's own default `/Decode` range for an *image* using `/Lab` (`decode.go`'s `colorSpace.decodeDefault`). |
| Separation, DeviceN | Phase 5 | Done | Implemented in `internal/image` (`colorspace.go`'s `resolveSeparationOrDeviceN`) by evaluating the color space's tint-transform function (`internal/function` - Type 0/2/3; Type 4 PostScript-calculator functions are unsupported, see that package's doc comment) and converting the result through the alternate color space. Available both as an image's `/ColorSpace` and - new in Phase 5 - as a content stream's `cs`/`CS`-selected fill/stroke color space (see the "Content streams and graphics" table's `sc`/`SC`/`scn`/`SCN` row). The `/DeviceN` `/Attributes` dictionary (colorant metadata, `/Process`, overprint simulation) is not inspected. |
| Pattern color space (tiling and shading patterns) | Phase 5 | Done | `cs`/`CS Pattern` is recognized and recorded (`internal/content/colorspace.go`). `scn`/`SCN` with a pattern name resolving to a shading pattern (`/PatternType 2`) or a colored tiling pattern (`/PatternType 1`) paints correctly - see the "Transparency and advanced graphics" table's Shading patterns and Tiling patterns rows; an uncolored tiling pattern (`/PaintType 2`) is explicitly rejected as unsupported. |

## Fonts

| Capability | Target phase | Status | Notes |
| --- | --- | --- | --- |
| Simple fonts: Type 1 (embedded, `/FontFile`) | Phase 11 | Done | Implemented in `internal/fonts/type1.go`: eexec/charstring decryption (including a PFA-style hex-armored eexec section, which some real-world producers embed even inside a PDF), a PostScript-source tokenizer for the decrypted Private dictionary's `/Subrs`/`/CharStrings`, and a full Type 1 Charstring interpreter (all path-construction operators, `hsbw`/`sbw`, local subroutine calls, and the `callothersubr`/`pop` flex and hint-replacement idiom real font-creation tools emit). `/FontFile` is read by `simple.go`'s `loadEmbeddedType1`, tried after `/FontFile2` and `/FontFile3`, with glyph lookup by charstring glyph name via `/Encoding` - the same non-symbolic lookup path the "OpenType/CFF" row below documents for CFF. Not implemented, matching that row's own equivalent gaps: a Type 1 font program's own built-in `/Encoding` array, and `seac` (recognized and reported as one unavailable glyph, never composed - the same deliberate scope decision as CFF's implicit-`seac` `endchar` form). A PDF `/FontFile` stream using a non-canonical name for the "read N binary bytes" private procedure (conventionally `RD` or `-\|`) is also a documented, narrow gap - see that file's `isType1RDToken` doc comment. |
| Simple fonts: TrueType (embedded, `/FontFile2`) | Phase 4 | Done | Implemented in `internal/fonts` (`truetype.go`: sfnt table directory, `head`/`maxp`/`loca`/`glyf` parsing, simple and composite glyph outlines; `cmap.go`: format 0/4/6 subtable parsing). Encoding resolution (`encoding.go`) covers StandardEncoding/WinAnsiEncoding/MacRomanEncoding (ASCII range exact; StandardEncoding's upper range is a documented gap - see that file's doc comment) and `/Differences` arrays (via a subset of the Adobe Glyph List plus the `uniXXXX` convention). |
| Composite fonts: Type 0 / CID (embedded, Identity-H/V and embedded CMap) | Phase 4, Phase 9 | Partial | Implemented in `internal/fonts/cid.go`: `/DescendantFonts`, `/W`/`/DW` widths, and outline extraction for both descendant kinds - CIDFontType2 (TrueType-based, via `/CIDToGIDMap`, `/Identity` or an explicit stream) and CIDFontType0 (CFF-based, via `cff.go`'s CID-keyed charset, which supplies CID-to-GID mapping directly since this descendant kind has no `/CIDToGIDMap` entry at all). `/Encoding` support (Phase 9, `cid.go`'s `loadType0Encoding`): the `Identity-H`/`Identity-V` names (a code is always 2 bytes, equal to its CID) and an embedded CMap *stream* - a full parser (`internal/fonts/cidcmap.go`) for PDF's CMap grammar (`codespacerange`, `cidrange`, `cidchar`, `usecmap` chaining), letting a code map to an arbitrary CID and, for a codespace mixing byte lengths, be decoded at more than one width (`Font.DecodeCodes`). A predefined CJK encoding *name* (e.g. `UniGB-UCS2-H`) resolves to a real CMap only if the embedding application opts in via `pdfviewer.WithPredefinedCMaps` (mirroring `WithFontSubstitution`'s own "opt-in, no bundled third-party data" pattern below) pointing at a real, disk-resident copy of Adobe's own CMap resource data (this package bundles none itself - a licensing/bundling decision, the same policy `docs/FONTS.md` documents for font files); `internal/fonts.DirectoryCMapSource` does the actual scanning (recursively, indexed by each file's own base name, matching Adobe's/Ghostscript's resource file naming convention). Without that option, or for a name the configured data does not cover, this falls back to a generic default width and `notdefGlyph` for every code exactly as before. Vertical writing (`Identity-V`) advances horizontally rather than vertically - a documented simplification, not a crash or misrender. |
| Non-embedded font fallback | Phase 4 | Done | Implemented in `internal/fonts` (`font.go`'s `notdefGlyph`): a small hollow placeholder box sized to the glyph's own advance width, painted for any code this package cannot resolve a real outline for (including via font substitution, below, when that is enabled but finds no candidate) - except a code positively identified as whitespace (a simple font's resolved encoding says so), which paints nothing instead. No system font service is ever queried (see the package doc comment); a non-embedded font's width still comes from `/Widths`/`/W` when present, a substitute font's own advance widths when substitution supplied one (see "Font substitution" below), or a generic default (`internal/fonts/simple.go`'s `defaultMissingWidth`, 500/1000 em) otherwise - this project ships no standard-14 (Helvetica, Times, ...) AFM metrics table. |
| Font substitution (finding a real outline for a font this package cannot extract one from directly) | Phase 4 | Done for simple fonts; Partial for Type 0/CID | Opt-in via `pdfviewer.WithFontSubstitution` (`options.go`) - a `Document` opened without it behaves exactly as before this feature existed. Implemented across `internal/fonts/substitute.go` (the `FontSource` interface and `matchFace`'s four-step algorithm: exact family match, then a small standard-14-to-category table, then the PDF's own descriptor Serif/FixedPitch flags, then give up) and `internal/fonts/directory_source.go` (`DirectorySource`, this package's only shipped `FontSource`: scans configured and/or GOOS-gated default platform directories for `.ttf`/`.ttc`/`.otf` files via `os.ReadDir`/`os.ReadFile` only - no CGO, subprocess, or platform font-service API, preserving this package's "no system font service" policy - and probes each with the existing Phase 2/3 sfnt/CFF parsing). Wired into `simple.go`'s `loadSimpleFont` fallback path only: once a match is found, its outline is used exactly like an embedded font's, and (`internal/fonts/font.go`'s `advanceWidthSource`) its own advance widths are used in place of the generic default when the PDF supplies no `/Widths` at all. **Not implemented for `cid.go`'s Type0/CID fonts** - a deliberate scope decision, not an oversight: matching a code to a substitute's own glyph needs to resolve that code to a Unicode rune, which is only possible for a simple font's `/Encoding`. Phase 10 (see "Text extraction" below) now parses a font's `/ToUnicode` CMap and can answer that question for a Type0 font too (`Font.TextForCode`), but wiring that answer into a substitution attempt here remains a separate, not-yet-implemented follow-on (`docs/PLAN2.md`'s backlog: "Type 0/CID font substitution") - so a non-embedded Type0 font still always falls back to `notdefGlyph` even with substitution enabled. A bundled last-resort font (so substitution has something to find even with no system fonts configured/available) was explicitly deferred by the user, pending a separate license decision - see `docs/FONTS.md`'s Phase 5. |
| Type 3 fonts (glyphs defined as content streams) | Not yet scheduled | Not started | A Type 3 font dictionary is accepted (via the same "simple font" code path as Type 1/TrueType) but its glyphs are never executed as content streams - it always falls back to `notdefGlyph`, using whatever `/Widths` it declares. Its own `/FontMatrix` (which can differ from the standard 1/1000 scale every other font type uses) is not applied to width interpretation, since no real outline is ever painted for one. Rare in practice; revisit if real-world demand appears. |
| OpenType/CFF (Type1C, CIDFontType0C) | Phase 4 | Done | Implemented in `internal/fonts/cff.go`: CFF INDEX/DICT/charset/FDSelect parsing and a full Type 2 Charstring interpreter (all path-construction and flex operators, subroutine calls, the arithmetic/storage escape operators), producing the same outline shape `truetype.go`'s `glyf` parsing does. `/FontFile3` is read for both a simple font's bare CFF/Type1C program (`simple.go`'s `loadEmbeddedCFF`, glyph lookup by charset name via `/Encoding`) and a CIDFontType0 descendant's CID-keyed program (`cid.go`, glyph lookup by CID via the charset's inverted CID-to-GID map) - either a bare CFF stream or an OpenType wrapper whose own `"CFF "` table holds it. The same support extracts outlines from an OTTO-flavored *candidate* font file found on disk (`probe.go`'s `FontFace.Outline`), closing this row's other half. Not implemented: a CFF program's own built-in Encoding table (16), the predefined Expert/ExpertSubset charsets (a documented, narrow gap - see `cff.go`'s doc comment), the deprecated implicit-`seac` 4-argument `endchar` form, and CFF2 (not needed by any font this project reads). |
| Text extraction (recovering Unicode text from a page, as opposed to painting it) | Phase 10 | Done | The root package's `Page.Text` (`text.go`, `page.go`) returns every glyph a page's own content stream shows, as a `[]TextGlyph` carrying its decoded Unicode text, baseline position, and advance width in the same page-point coordinate space `Page.Bounds` reports. Implemented as a genuinely separate walker (`internal/content/text_extract.go`'s `ExtractText`), not a mode flag on the text-*painting* interpreter, per docs/PLAN.md's original Phase 4 plan - it understands only the operators that can affect what text exists or where it sits (`q`/`Q`/`cm`, the text-object and text-state/positioning/showing operators) and never fails on account of a feature `Render` itself does not support (an unsupported image, color space, shading, or pattern), since none of that affects a page's text. Unicode recovery (`internal/fonts/tounicode.go`'s `parseToUnicodeCMap`, reusing `cidcmap.go`'s lexer-based CMap grammar machinery Phase 9 built) parses a font's `/ToUnicode` CMap (`beginbfchar`/`beginbfrange`, including both the "increment a destination value" and "explicit destination array" `beginbfrange` shapes, and multi-character/ligature destinations) via `Font.TextForCode`, falling back to a simple font's own resolved `/Encoding` when no `/ToUnicode` entry exists at all; a Type0/CID font with neither yields a correctly positioned glyph with empty text rather than a guess. **Not implemented:** recursion into a Form XObject's own content stream (`Do` naming a `/Form` is simply skipped, exactly like every other painting operator `ExtractText` does not interpret) - a documented scope limitation (`internal/content/text_extract.go`'s own doc comment), not an oversight; `/ToUnicode`'s own rare `usecmap` operator (unlike Phase 9's CID CMaps, a `/ToUnicode` CMap building on a predefined UCS resource via `usecmap` is uncommon enough in practice that this was deliberately left unimplemented - see `tounicode.go`'s doc comment). |

## Transparency and advanced graphics

| Capability | Target phase | Status | Notes |
| --- | --- | --- | --- |
| Alpha constants and basic transparency (`ca`/`CA`) | Phase 5 | Done | Implemented via `gs` (`internal/content/extgstate.go`'s `applyExtGState`): `/ca`/`/CA` set `graphics.State.FillAlpha`/`StrokeAlpha` (both part of the graphics state, saved/restored by `q`/`Q`), which attenuate every fill, stroke, image, and shading `DrawOp` (`internal/raster.Canvas`'s compositing formula, `blendChannel`). No transparency *groups* exist (see the next row), so alpha compositing is against the single, always-opaque page canvas rather than an isolated group buffer - correct for how PDF renders in the common case of un-grouped content, but not equivalent to a full group-aware compositor for content that specifically relies on group isolation or a non-`/Isolated` group's backdrop semantics. |
| Transparency groups and blend modes | Phase 5 | Partial | Blend modes: `gs`'s `/BM` sets `graphics.State.BlendMode`, applied identically for fill/stroke/image/shading painting. Only PDF's six *separable* blend modes are implemented (Multiply, Screen, Darken, Lighten, Difference, Exclusion - `internal/graphics/blend.go`'s `Blend`); the four non-separable modes (Hue, Saturation, Color, Luminosity) and the remaining separable ones this project chose not to implement (ColorDodge, ColorBurn, HardLight, SoftLight, Overlay) resolve to Normal, per the specification's own documented fallback for an unsupported blend mode. Transparency *groups* themselves (`/Group` on a Form XObject, isolated/knockout compositing semantics) are not implemented - a Form XObject's content flattens directly onto the page canvas (see "Form XObjects" below) regardless of any `/Group` entry it declares. |
| Soft masks | Phase 5 | Not started | Per-image `/SMask` (Phase 3) is implemented - see "Images" below. An ExtGState-level `/SMask` (deriving a soft mask from an entire separate transparency group's luminosity or alpha, applied to everything painted afterward) is not: `gs` silently ignores a `/SMask` entry. |
| Tiling patterns | Phase 5 | Partial | Implemented in `internal/content` (`tilingpattern.go`'s `buildTilingPattern`) for colored (`/PaintType 1`) patterns: one repetition of the pattern cell is rendered once to a small, reusable image (`internal/raster.RenderTransparent`, which - unlike the ordinary `Render` every other rendered result in this project uses - preserves real per-pixel transparency, since the page underneath must show through wherever the cell's own content does not paint) and then sampled with wraparound ("tile") addressing (`graphics.DrawOp.Repeat`) to cover however large a shape the pattern actually fills. Uncolored (`/PaintType 2`) patterns - whose cell relies entirely on externally supplied color operands rather than painting its own - are not supported and return an error wrapping `ErrUnsupported`. Blend modes used *inside* a pattern cell's own content are not honored while rendering the tile (always treated as Normal - see `RenderTransparent`'s own doc comment); this is a documented simplification, not expected to matter for the flat-colored motifs tiling patterns are used for in practice. |
| Shading patterns (axial, radial, function-based; other types as needed) | Phase 5, 13a | Partial | Implemented in `internal/content` (`shading.go`'s `resolvePatternPaint`) for `/PatternType 2` over any shading type `buildShading` itself supports (axial, radial, function-based - not yet mesh, see the "Content streams and graphics" table's Shading row): the pattern's own `/Matrix` is combined with the *default* (not current) coordinate system of the content stream that defined it, per the specification, so the pattern looks identical regardless of what CTM happens to be active wherever it is later selected or used to paint. A shading pattern paints only the shape it fills or strokes (`internal/raster`'s `Canvas.FillShading`), unlike the `sh` operator's whole-clip painting. |

| Capability | Target phase | Status | Notes |
| --- | --- | --- | --- |
| Annotation appearance streams (rendering an annotation's existing visual appearance) | Phase 5 | Done | Implemented in `internal/annotation` (page-level `/Annots` resolution, `/F` Hidden/NoView flag filtering, `/AP` `/N` single-stream or `/AS`-selected multi-state lookup, and the BBox-to-Rect mapping algorithm, 12.5.5) plus the root package's `annotations.go`, which executes each resolved appearance by reusing `internal/content`'s Form XObject machinery directly (an appearance stream *is* a Form XObject). ## Explicit non-goals

These are recorded here (duplicating the docs/PLAN.md's "Non-goals for the
Initial Release" section) so this matrix is a complete answer to "is X
supported", including the things this project does not intend to
support:

- PDF creation or editing (this project reads and renders; it does not
    write PDF files).
- Annotation/form interactivity, JavaScript actions, or any other
    scripting behavior embedded in a PDF.
- Guaranteed recovery of every malformed or hostile file; only bounded,
    non-panicking, classified-error behavior is guaranteed (see the
    "Dependency and safety policy" section of the PLAN).
